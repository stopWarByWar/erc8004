# ERC-8183 Job Indexer Spec（commerce_jobs 快照）

本文面向后端/索引器开发，定义 **ERC-8183 Job 相关事件**如何写入数据库快照表 `commerce_jobs`，确保 UI 的 Job Detail / Job List 展示口径一致，且满足：

- **全部时间字段使用链上时间**（`block_timestamp` 或合约事件字段）
- **不使用 `eth_getTransactionReceipt`** 拉取结算拆分（避免浪费 RPC）
- **幂等**：重复消费日志不会导致数据错误
- **快照优先**：UI 概览读 `commerce_jobs`，证据读 `commerce_actions`

设计基线：[docs/designs/202604101000_erc8183-job.md](../../../designs/202604101000_erc8183-job.md) 第 4~5 章。

实现参考（当前仓库）：

- Indexer：`indexer/processor/commerce.go`
- Token 历史 USD：`indexer/processor/token.go`（`GetHistoricalUSDBudget(..., blockTimestamp)`）
- Model：`model/types.go`（`CommerceJob`）、`model/commerce.go`（`FetchOrCreateCommerceJob`、`UpsertCommerceJob`）
- Migration：`migrations/202604131300_commerce_jobs_payment_breakdown.sql`

## 1. 数据模型与快照原则

### 1.1 `commerce_jobs` 的职责

- **职责**：保存每个 Job 的“当前状态快照”，用于 Job Detail 首屏与 Job List 列表快速查询。
- **权威事实来源**：链上事件日志（由 indexer 解析 + 按事件更新字段）。
- **不做**：复杂统计聚合（图表/统计应由专用 API 聚合或读 actions/scores/stats 口径）。

### 1.2 主键与唯一性

- 逻辑唯一键：`(chain_id, commerce_contract, job_id)`
- Upsert 冲突策略：`ON CONFLICT(chain_id, commerce_contract, job_id) DO UPDATE SET ...`

### 1.3 时间字段（强约束）

- `commerce_jobs.updated_at`：必须来自当前处理事件所在 log 的 **`block_timestamp`**（unix 秒）。
- `expired_at/submitted_at/completed_at`：来自合约事件字段或当次 log 的 on-chain 时间（以合约语义为准）。
- **禁止**任何 `time.Now()` 回填；`UpdatedAt = 0` 必须视为错误并拒绝写入（避免统计口径混入系统时间）。

## 2. 事件订阅与解析

### 2.1 订阅事件集合（FilterLogs）

Job 生命周期与结算相关事件需要被订阅（至少）：

- `JobCreated`
- `ProviderSet`
- `BudgetSet`
- `JobFunded`
- `JobSubmitted`
- `JobCompleted`
- `JobRejected`
- `JobExpired`
- **结算拆分（无需 receipt）**
  - `PaymentReleased(jobId, provider, amount)`
  - `PlatformFeePaid(jobId, treasury, amount)`
  - `EvaluatorFeePaid(jobId, evaluator, amount)`

> 约束：`PaymentReleased/PlatformFeePaid/EvaluatorFeePaid` 必须通过 `FilterLogs` 直接消费，不能在 `JobCompleted` 时通过 `eth_getTransactionReceipt` 反查。

### 2.2 解析输入（每条 log 必备字段）

每条日志进入 handler 时，必须拥有以下信息：

- `chain_id`
- `commerce_contract`
- `job_id`
- `block_number`
- `tx_hash`
- `log_index`
- `block_timestamp`（unix 秒）

## 3. 事件 → 快照字段更新映射（P0）

对任意事件，流程固定：

1. 解析事件，得到 `job_id` 与事件字段
2. `FetchOrCreateCommerceJob(chainID, contract, jobID)` 获取当前快照（或初始化）
3. 按事件类型更新 `CommerceJob` 字段
4. 写入审计字段（见 4.2）
5. `UpsertCommerceJob(job)` 保存

### 3.1 字段映射表

| 事件 | 更新字段（仅列核心） |
|---|---|
| `JobCreated` | `status=open`，`client`，`hook_address`，`expired_at`，`description` |
| `ProviderSet` | `provider`，`evaluator` |
| `BudgetSet` | `budget`，`payment_token`，`token_symbol`，`budget_usd` |
| `JobFunded` | `status=funded` |
| `JobSubmitted` | `status=submitted`，`submitted_at` |
| `JobCompleted` | `status=completed`，`completed_at` |
| `JobRejected` | `status=rejected` |
| `JobExpired` | `status=expired` |
| `PaymentReleased` | `paid_amount`，`paid_amount_usd` |
| `PlatformFeePaid` | `platform_fee_amount`，`platform_fee_usd` |
| `EvaluatorFeePaid` | `evaluator_fee_amount`，`evaluator_fee_usd` |

### 3.2 USD 换算（Budget/Paid/Fee）

- **换算函数**：`GetHistoricalUSDBudget(chainID, paymentToken, tokenSymbol, amount, blockTimestamp)`
- **时间基准**：必须使用该事件所在 log 的 `block_timestamp`（链上时间）。
- **写入时机**：
  - `budget_usd`：在 `BudgetSet` 时写入（BudgetSet 时刻估值）
  - `paid_amount_usd`：在 `PaymentReleased` 时写入（complete 时刻估值）
  - `platform_fee_usd`：在 `PlatformFeePaid` 时写入
  - `evaluator_fee_usd`：在 `EvaluatorFeePaid` 时写入

### 3.3 “非 completed 的 paid/fee”口径

- 写入层面：结算事件只会在合约实际 emit 时出现；未完成的 job 不应被写入 paid/fee（保持 0 或缺省）。
- 展示层面：UI 对 `status != completed` 的 Paid/Fee 显示 `—`（避免用户将 0 误读为“已结算为 0”）。

## 4. 幂等、顺序与审计

### 4.1 幂等策略

- 快照表 `commerce_jobs`：通过 `UpsertCommerceJob` 实现幂等更新。
- 事件明细表 `commerce_actions`（不在本文详述）：应使用唯一键（如 `tx_hash + log_index` 或项目既有 unique）+ `ON CONFLICT DO NOTHING` 避免重复写入。

### 4.1.1 `commerce_actions`（图表聚合必需的最小字段）

为支撑 Job Browser 的时间序列图表聚合（created jobs / platform fee over time），`commerce_actions`（或其等价表/视图）至少需要具备：

- 定位键：`chain_id`、`commerce_contract`、`job_id`
- 事件键：`tx_hash`、`log_index`（或等价 unique key）
- 时间：`block_timestamp`（unix 秒，on-chain）
- 类型：`action_type`（至少覆盖 `JobCreated`、`PaymentReleased`、`PlatformFeePaid`、`EvaluatorFeePaid`）
- 金额（USD）：对金额类事件（`PaymentReleased/PlatformFeePaid/EvaluatorFeePaid`）写入 `amount_usd`（使用对应 log 的 `block_timestamp` 进行历史估值）

> 说明：`platform_fee_usd_over_time` 必须使用事件发生额聚合，因此需要 actions 侧的 `amount_usd`，不能依赖 `commerce_jobs.platform_fee_usd` 快照字段（快照无法表达“当期发生额”）。

### 4.2 审计字段写入

每次更新 `commerce_jobs` 都必须写入：

- `latest_block_number = log.block_number`
- `latest_tx_hash = log.tx_hash`
- `latest_action_uid`：
  - 若本次事件会写入一条对应 `commerce_actions`，则填该 action 的 uid
  - 若无法关联（实现上未返回 uid），允许为 0，但后续应补齐（P1）
- `updated_at = log.block_timestamp`（强约束）

### 4.3 事件到达顺序（容错）

由于跨 RPC/重放/多 topic 订阅，事件可能出现乱序或先后分离：

- `PaymentReleased/PlatformFeePaid/EvaluatorFeePaid` 可能在 `JobCompleted` 之后到达（甚至先于 JobCompleted，被重放时也可能出现）
- 处理原则：
  - `FetchOrCreateCommerceJob` 必须能在“快照不存在”时返回默认 job（至少带 chain/contract/job_id/status=open）
  - 任何结算事件到达时：
    - 不要求 `status=completed` 才写入金额字段（以事实为准）
    - 但 `updated_at` 仍以该结算事件 log 的时间为准

## 5. 失败处理与可观测性

### 5.1 错误分级（建议）

- **不可恢复 / 需要修复数据或代码**
  - `UpdatedAt == 0`（链上时间缺失）
  - ABI 解码失败（topic 命中但 data 不符合）
- **可恢复（允许重试/跳过）**
  - 历史价格源不可用：`*_usd` 写 0 或保持默认，同时记录 warning（不应阻塞快照写入）
  - DB 短暂错误：按 indexer 既有重试策略处理

### 5.2 日志与指标（最小）

- handler 级别：`chain_id/contract/job_id/action/tx_hash/log_index/block_timestamp`
- 写入成功：记录 `updated_at` 与关键金额字段（budget/paid/fee）
- 价格失败：记录 token + block_timestamp + amount + error

---

## 6. 验收 Checklist（Indexer）

- [ ] `commerce_jobs.updated_at` 全量来自链上 `block_timestamp`（无 `time.Now()`）
- [ ] `BudgetSet` 会写 `budget_usd`
- [ ] 结算拆分通过 `FilterLogs` 写入 `paid_amount(_usd)` / `platform_fee_*` / `evaluator_fee_*`，不调用 receipt
- [ ] 重放同一批 logs 不会产生不一致（幂等）
- [ ] 乱序到达的结算事件不会导致 handler 崩溃（可先创建默认 job）
