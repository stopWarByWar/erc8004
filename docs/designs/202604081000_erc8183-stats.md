## 一、背景与目标

在现有的 `GET /agent/commerce/scores` 接口中，Commerce Score 仅返回聚合后的摘要数据（总量、成功率等），无法支撑前端做**统计分析图表**。

本设计新增 `GET /agent/commerce/stats` 端点，为前端提供三族图表数据：
1. **Action 类型分布** — 各 action 类型（created/funded/submitted/completed/rejected/expired）的数量
2. **时间序列趋势** — 24h / 7d / 30d 三个时间窗口内的完成数、驳回数、成功率变化
3. **Budget 分布** — 按 commerce_contract（token）分组，按统计分位数划分 small/medium/large 桶

所有数据按 **Role** 维度展开（provider / client / evaluator），无数据的 role 不返回。

## 三、Response 结构

```json
{
  "code": 0,
  "status": "success",
  "data": {
    "stats": {
      "action_breakdown": {
        "provider": {
          "job_created": 10,
          "job_funded": 8,
          "job_submitted": 6,
          "job_completed": 5,
          "job_rejected": 1,
          "job_expired": 0
        },
        "client": { ... }
      },
      "time_series": {
        "24h": [
          {
            "bucket": 1744124400,
            "completed_count": 3,
            "rejected_count": 0,
            "success_rate": 1.0
          }
        ],
        "7d": [...],
        "30d": [...]
      },
      "budget_distribution": {
        "provider": {
          "0x123...abc": {
            "total_count": 50,
            "buckets": {
              "small":  { "count": 20, "max_amount": "1000" },
              "medium": { "count": 20, "max_amount": "5000" },
              "large":  { "count": 10, "max_amount": "50000" }
            }
          }
        }
      }
    }
  }
}
```

### Action Breakdown

- Key：`provider` / `client` / `evaluator`
- Value：每个 action 的 count
- 无数据的 role 直接省略（不返回空对象）

### Time Series

- `24h`：1 小时桶，共 24 个桶
- `7d`：6 小时桶，共 28 个桶
- `30d`：1 天桶，共 30 个桶
- `bucket`：Unix timestamp（桶的起始时间）
- `success_rate`：该桶内 `completed / (completed + rejected)`（rejected 仅统计 `job_rejected`，不含 expired），若两者均为 0 则为 0

### Budget Distribution

- 第一层 Key：role（provider / client / evaluator）
- 第二层 Key：`commerce_contract` 地址（作为 token 的 proxy）
- `total_count`：该 contract 下，action 为 `job_completed` 或 `job_rejected` 的总行为数
- `buckets`：按 33rd / 66th 百分位数将 budget 从小到大排序后分桶（仅统计 `job_completed` + `job_rejected`，不含 `job_expired`）
  - `small`：低于 33rd percentile
  - `medium`：33rd ~ 66th percentile
  - `large`：高于 66th percentile
  - **样本量 < 3**：不拆分，直接返回一个 unnamed 桶（仅有 `count` 和 `max_amount`）
- `max_amount`：该桶内最大的 job_budget 值（原始数值，string 格式），前端自行做 token 单位换算

**分桶逻辑说明**：因为不同 contract 对应不同 token（BNB / USDT / 自定义 ERC-20），token 价值不同，不能用固定阈值。改用统计分位数，同一 contract 内的 budget 可比较。前端负责 token 的 USD 换算和展示。

## 四、时间窗口计算

当前时间取该 agent 在 `commerce_actions` 表中最新一条记录的 `block_timestamp`。

若该 agent 尚无任何 action，则 fallback 到系统时间 Unix timestamp。

三个窗口：
- `24h`：window_start = now - 86400 秒，bucket_duration = 3600 秒（1 小时）
- `7d`：window_start = now - 604800 秒，bucket_duration = 21600 秒（6 小时）
- `30d`：window_start = now - 2592000 秒，bucket_duration = 86400 秒（1 天）

## 五、模型层实现

### 5.1 新增查询函数（model/commerce.go）

**GetCommerceActionCountsByRole(uid uint64)**
- SQL：`SELECT role, action, COUNT(*) FROM commerce_actions WHERE agent_uid = ? GROUP BY role, action`
- 返回：嵌套 map `map[role]map[action]int`

**GetCommerceTimeSeries(uid uint64, windowStart, windowEnd, bucketDuration uint64)**
- SQL：`(block_timestamp / bucketDuration) * bucketDuration` 作为 bucket_key，按 bucket 分组 SUM completed/rejected
- 利用现有索引：`idx_ca_agent_timestamp` on `(agent_uid, block_timestamp)`
- 返回：`[]TimeBucketAgg{BucketTime, CompletedCount, RejectedCount, SuccessRate}`

**GetCommerceBudgetDistributionByContract(uid uint64)**
- 先查该 agent 所有终态 budget 值，计算 33rd / 66th 百分位数
- 再查各 contract 下各桶的 count 和 max_amount
- 返回：`[]ContractBudgetAgg{Role, Contract, TotalCount, SmallCount, SmallMax, MediumCount, MediumMax, LargeCount, LargeMax}`

### 5.2 新增聚合结构

```go
type TimeBucketAgg struct {
    BucketTime    uint64
    CompletedCount int
    RejectedCount  int
    SuccessRate    float64
}

type ContractBudgetAgg struct {
    Role         string
    Contract     string
    TotalCount   int
    SmallCount   int
    SmallMax     float64
    MediumCount  int
    MediumMax    float64
    LargeCount   int
    LargeMax     float64
}
```

## 六、API 层实现

### 6.1 Types（server/api/types/types.go）

新增：
- `CommerceStatsResponse`（顶层）
- `CommerceStats`（stats 字段）
- `ActionBreakdown`（map[role]ActionCounts）
- `ActionCounts`（6 个 action 字段）

- `TimeBucket`
- `BudgetDistribution`（map[role]map[contract]ContractBudgetStats)）

- `BudgetBuckets`（small/medium/large）
- `BudgetBucketStat`（count, max_amount）

### 6.2 Logic（server/api/logic/commerceLogic.go）

新增：
- `CommerceStatsParams` struct（UID, Now）
- `GetCommerceStats(CommerceStatsParams)` → `*types.CommerceStats`
- 百分位数计算逻辑在 logic 层实现

### 6.3 Handle（server/api/handle/commerceHandle.go）

新增：`GetCommerceStatsHandler`
- 解析 `uid` query 参数
- 查询最新 `block_timestamp` 作为 Now
- 调用 `logic.GetCommerceStats`
- 返回 `SuccessResp(gin.H{"stats": stats}, c)`

### 6.4 Router（server/api/router.go）

新增路由：`r.GET("agent/commerce/stats", handle.GetCommerceStatsHandler)`

## 七、索引与查询效率

| 查询 | 索引 |
|------|------|
| Action breakdown | `GROUP BY role, action WHERE agent_uid=?` — 全表扫描 agent_uid 行 |
| Time series | `idx_ca_agent_timestamp (agent_uid, block_timestamp)` — 覆盖时间范围过滤 |
| Budget distribution | `WHERE agent_uid=? AND action IN ('job_completed','job_rejected') GROUP BY role, contract` — 仅扫终态行 |

三条查询均以 `agent_uid` 为过滤条件，扫描范围仅为该 agent 的历史行为数据。

---

## 八、空状态处理

- Role 无数据：不返回该 role 的 key
- Time series bucket 无数据：该 bucket 不出现在数组中（只返回有数据的桶）
- Budget 某桶无数据（count = 0）：该桶不出现

## 九、验证计划

1. `go build ./server/main.go` — 编译通过
2. `go test ./...` — 现有测试通过
3. 手动测试：
   - `curl "http://localhost:8080/agent/commerce/stats?uid=1"` 返回合法 JSON
   - `action_breakdown` 包含 provider/client/evaluator（无数据的 role 省略）
   - `time_series` 三个窗口均有数据（若该 agent 有历史数据）
   - `budget_distribution` 按 contract 分组，桶内 max_amount 非递减
4. 边界测试：
   - uid 不存在：返回空 stats（所有 map 均为空）
   - uid 存在但无 commerce_actions：返回空的 action_breakdown 和 time_series，budget_distribution 为空
